# 基于 SpringBoot 的校园活动管理系统 —— 总体规划

> 论文题目：基于 SpringBoot 的校园活动管理系统设计与实现
> 定位：一套能跑、能讲、能查重过关的本科毕业设计（1.2 万字论文 + 可运行系统 + 答辩材料）
> 已确认：前端 Vue2 + Element UI；交付全套材料；系统需具备换机可移植性

---

## 一、先解决三个"致命问题"

写毕设最怕的不是功能做不出来，而是做了之后论文重复率高、AI 率高、换台电脑演示不了。所以规划的第一层不是功能，而是这三件事：

| 风险 | 常见后果 | 本规划的对策 |
|---|---|---|
| 论文查重率高 | 直接退回重写 | 需求分析用本校真实调研数据；技术章节写成"选型对比+本项目用法"；数据库/接口/测试用例章节天然低重复 |
| AI 检测率高 | AIGC 检测不通过 | 禁止模板句式清单（见 6.3）；写"问题—尝试—解决"的工程细节，带真实报错和数字；图表全部手绘 |
| 演示环境跑不起来 | 答辩现场翻车 | 单 jar 部署（前端打进 SpringBoot）+ H2 免安装演示模式 + 一键启动脚本 + 换机验证清单 |

这三条决定了下面所有技术选型都偏向"稳"，不偏向"炫"。

## 二、系统定位与差异化亮点

题目很常规（校园活动管理系统），大概率撞题。**撞题不可怕，撞功能实现才可怕**。所以系统在"发布—报名—签到—评价"这条主线上，做三个属于你自己的设计点，每个都能在论文里单独成节，查重查不到，AI 也编不出细节：

### 亮点 1：报名名额的并发安全控制
绝大多数同类系统是 `select` 查名额 → 判断 → `update` 减名额，20 个人同时抢 1 个名额就会超卖。
本系统改用**数据库条件原子更新**：

```sql
update activity
set signed_count = signed_count + 1
where id = #{id} and signed_count < capacity and status = 2;
```

判断 `affectedRows == 1` 决定报名成功与否，失败则回滚报名记录。论文第 5 章可写完整过程：怎么发现超卖（并发测试脚本）、为什么不用悲观锁、为什么不用 Redis、压测 50 并发的实际结果。

### 亮点 2：签到码时效 + 爽约（违约）记录机制
- 组织者在活动开始前生成 **6 位数字签到码**，默认有效期 30 分钟，可手动刷新（刷新即旧码失效）。
- 学生输入签到码签到，系统校验：是否已报名、是否在有效期内、是否在活动时间窗口内、是否重复签到。
- **爽约记录**：活动结束后，已报名但未签到的自动标记为"爽约"，累计爽约 ≥2 次的学生，30 天内不能报名新活动（可配置）。这条规则是真实校园管理里需要的，同类系统基本没有。

### 亮点 3：活动质量分与排序
用 `签到率 × 40% + 平均评分归一化 × 40% + (1 - 取消率) × 20%` 算一个 0~100 的活动质量分，用于首页"热门活动"排序和组织者的活动复盘。计算逻辑写在 Java 层，不依赖数据库方言函数（对 H2 兼容很重要）。

> 这三个点共同的特点是：**逻辑不复杂但细节多**。细节多 = 论文有东西写 = 查重查不到。

## 四、角色与权限

三种角色，用 `user.role` 字段 + 登录拦截器 + 自定义 `@RequireRole` 注解（AOP 校验）实现，不引入 Spring Security（配置重、调试难、论文写起来也容易撞车）。

| 角色 | 能做什么 |
|---|---|
| 学生 student | 浏览活动、报名/取消、签到、评价、看自己的记录和消息 |
| 组织者 organizer | 学生全部功能 + 发布/编辑/取消活动、看报名名单、管理签到、看本活动统计 |
| 管理员 admin | 审核活动、管理用户、管理分类、发布公告、看平台统计 |

登录后 JWT 中携带 `userId + role`，前端路由守卫按角色放行菜单，后端拦截器二次校验（前端拦截只是体验，后端才是安全边界——这句可以写进论文）。

## 五、功能模块详细清单

### M1 用户模块
- 注册：学号/工号唯一校验、密码 BCrypt 加密（不存明文）、角色选择（学生/组织者，管理员由后台指定）
- 登录：账号密码 → JWT，有效期 2 小时，前端存 localStorage
- 个人信息：昵称、手机、邮箱、头像上传（存本地 `./upload/`，通过静态资源映射访问）
- 修改密码：校验原密码

### M2 活动模块
- 发布（组织者）：标题、分类、封面图、一句话简介、详细内容、地点、开始时间、结束时间、报名截止时间、人数上限、是否需要报名审核
- 状态机：`草稿(0) → 待审核(1) → 已发布(2) / 已驳回(3)`；`已发布 → 已取消(4) / 已结束(5)`，由定时任务自动流转
- 审核（管理员）：通过 / 驳回（必填理由），驳回后组织者可修改重提
- 取消（组织者）：已有报名时需二次确认，取消后给所有报名者推送站内消息
- 学生端：列表（分类 Tab + 关键词 + 时间范围 + 分页）、详情（含已报名人数/剩余名额/报名状态）、首页热门推荐

### M3 报名模块
报名前置校验（顺序很重要，论文里可以列成表）：
1. 活动状态是否为"已发布"
2. 当前时间是否早于报名截止时间
3. 是否已报名（唯一索引兜底）
4. 是否触发爽约限制
5. 名额原子扣减（亮点 1）

取消报名：仅报名截止前可取消，取消名额返还（同样用条件更新 `signed_count > 0`）。

### M4 签到模块
- 组织者：生成/刷新签到码（显示倒计时）、查看已签到/未签到名单、手动补签（需填备注）、导出名单
- 学生：在"我的报名"里输入签到码 → 校验 → 签到成功
- 定时任务：活动结束后把未签到的报名记录置为"爽约"，同时累加用户 `violation_count`

### M5 评价模块
- 前置条件：已报名且活动已结束（避免刷好评）
- 一人一条（`unique(activity_id, user_id)`），1~5 星 + 文字（10~200 字）+ 可选匿名
- 活动详情页展示评价列表（分页）与评分分布图
- 组织者不可评价自己的活动

### M6 统计模块
- 活动维度：报名人数、签到人数、签到率、平均分、评分分布（柱状/饼图）
- 组织者维度：发布活动数、累计参与人次、平均签到率
- 平台维度：近 6 个月活动趋势（折线）、分类占比（饼图）、TOP5 热门活动（横向柱状）
- **所有聚合在 Java 层完成**（查明细再 `stream` 聚合），避免 `date_format`、`group_concat` 等方言函数导致 H2 跑不通

### M7 消息通知
- 触发场景：活动审核通过/驳回、活动被取消、活动开始前 1 小时提醒（定时任务）、报名成功
- 站内消息列表 + 未读数（前端 60 秒轮询一次，不做 WebSocket，够用且不复杂）

### M8 后台管理
用户管理（禁用/启用、重置密码、调整角色）、分类管理（增删改、排序）、活动审核、公告管理

> **明确不做**：聊天、支付、地图定位、微信登录、微服务、Redis 缓存、消息队列。每加一个都是给自己挖坑。

## 六、数据库设计

### 6.1 表清单（8 张）

| # | 表名 | 说明 | 关键点 |
|---|---|---|---|
| 1 | `sys_user` | 用户 | 学号唯一；`violation_count` 爽约次数；status 启禁用 |
| 2 | `activity_category` | 活动分类 | 名称唯一、排序、启禁用 |
| 3 | `activity` | 活动主表 | **冗余字段 `signed_count`**（并发控制用）；`checkin_code` + `code_expire_time`；`version` 乐观锁 |
| 4 | `activity_registration` | 报名记录 | `unique(activity_id, user_id)`；status：1 已报名 / 2 已签到 / 3 已取消 / 4 爽约 |
| 5 | `activity_review` | 评价 | `unique(activity_id, user_id)`；score 1~5 |
| 6 | `notice` | 站内消息 | `user_id` 为 NULL 表示广播 |
| 7 | `sys_notice` | 平台公告 | 管理员发布，首页展示 |
| 8 | `sys_config` | 参数配置 | 爽约阈值、爽约封禁天数、签到码有效期——放配置表里，论文里可讲"可配置化" |

> 签到码直接放在 `activity` 表（两列），不单独建表：签到码刷新即覆盖，没有保留历史的价值，少一张表少一堆代码。

### 6.2 E-R 关系
- 用户(1) —< 活动(N)：组织者发布
- 用户(M) —< 报名 >—(N) 活动：多对多，中间表 `activity_registration`
- 用户(M) —< 评价 >—(N) 活动
- 分类(1) —< 活动(N)

### 6.3 索引设计（论文里可单列一节）
- `activity(status, start_time)` 列表查询
- `activity(organizer_id)` 我的活动
- `activity_registration(user_id, status)` 我的报名
- `activity_registration(activity_id, status)` 名单查询
- `activity_registration` 唯一索引 `(activity_id, user_id)` —— 防重复报名的最后一道防线

## 九、部署架构与可移植性（Vercel + SQLPub + 便携运行时）

按你的方案：**前端 Vercel、数据库 SQLPub、本地跑便携临时环境**。这套组合确实灵活（代码一拷、库在云上、前端在云上），但有三个坑必须先说清楚，否则答辩现场容易翻车。

### 9.0 三个必须先知道的坑

| 坑 | 具体表现 | 处理办法 |
|---|---|---|
| **HTTPS 混合内容** | Vercel 是 https，后端在本地是 `http://localhost:8080`，浏览器会直接拦掉 API 请求，控制台报 `blocked:mixed-content` | 在线形态必须给后端也配 https；**答辩现场一律用"单 jar 同源 http"形态**，页面和接口同一个地址，零跨域零混合内容 |
| **vercel.app 在大陆被 DNS 污染** | 国内网络经常打不开 `xxx.vercel.app`；Vercel 官方知识库也承认大陆无节点、可能很慢或加载失败 | 绑自定义域名，CNAME 指向 `cname-china.vercel-dns.com`；或者接受"仅境外/校园网访问"，现场用本地形态 |
| **SQLPub 免费版有硬限制** | 1 个 schema、0.5GB 存储、1.8 万请求/小时、30 个并发连接、共享实例；超存储会**锁库**；免费版**无自动备份**；Serverless 缩容后首连有数秒冷启动 | 建表与演示数据全部脚本化进仓库，随时可重建；后端保留 H2 兜底 profile；连接池上限压到 10，连接超时 15s |

> 结论：**Vercel + SQLPub 作为"在线展示形态"很好，但不能作为唯一的演示形态。** 答辩现场必须有断网也能跑的方案，这就是下面形态 A/B 存在的理由。

### 9.1 一套代码，三种运行形态

| 形态 | 场景 | 前端 | 后端 | 数据库 | 依赖 |
|---|---|---|---|---|---|
| **A 单 jar（答辩主力）** | 现场演示、交作业 | 打包进 jar 的 static | 本地启动 | SQLPub 云端 | 便携包内含 JRE，双击即跑 |
| **B 纯离线** | 断网、SQLPub 抽风、宿舍网差 | 同上 | 同上 | 内置 H2 文件库 | 同上，零网络 |
| **C 在线展示** | 简历、老师随时点开看 | Vercel 静态托管 | 需一个 HTTPS 后端（Render/Zeabur，可选做） | SQLPub 云端 | 无 |

三种形态共用同一份代码和同一套 SQL，靠 `application-{profile}.yml` 切换，切换成本是一行启动参数。

### 9.2 数据库：SQLPub 接入要点
- 免费版共享实例，MySQL **8.0 / 8.4**（本项目按 8.0 语法写，不碰 8.4 新特性）
- 连接信息从控制台详情页取：Host / Port / User / Password / Database，走公网，**开 SSL**
- 驱动 `mysql-connector-java 8.0.33`，连接串：
  `characterEncoding=utf8&serverTimezone=Asia/Shanghai&useSSL=true&connectTimeout=15000&socketTimeout=30000&allowPublicKeyRetrieval=true`
- 连接池 Hikari：`maximum-pool-size: 10`（远低于 30 并发上限，留余量给 Web SQL 客户端和排查工具）
- **公网 RTT 一般 20~80ms**，所以：列表页一次查询到位（JOIN 分类/组织者），禁止循环里查库（N+1），分页在 SQL 层做，统计尽量一次聚合
- 免费版无自动备份 → `db/schema.sql` + `db/data.sql` 就是唯一可信来源，每次改表同步更新脚本

> **2026-11-18 实测**：SQLPub 共享实例实际是 **MySQL 8.4.3**（自建发行版），`mysql6.sqlpub.com:3311` 走公网 TLS。
> 用 `scripts/DbInit.java`（纯 JDBC，不依赖 mysql 客户端）跑完 `schema.sql`（16 条）+ `indexes.sql`（7 条）+ `data.sql`（8 条），**全部成功、零失败**。

### 9.3 前端：Vercel 部署要点
- `VUE_APP_API_BASE` 走环境变量：本地开发留空走代理，Vercel 上填后端公网地址，`npm run build` 时注入
- Vue Router 用 **history 模式** 时必须加 `vercel.json`，否则刷新子页面 404（几乎人人都踩，论文里也能写一笔）：
  ```json
  { "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }] }
  ```
- 后端 CORS 放行 `http://localhost:*`、`https://*.vercel.app` 和你的自定义域名；JWT 放请求头而非 Cookie，避开 SameSite 问题
- 构建产物带 hash，交给 Vercel CDN 缓存

### 9.5 为了三种形态都能跑，代码上必须守的约束
1. **不用数据库方言函数**：`date_format`、`group_concat`、`ifnull` 一律不用，日期格式化与聚合放 Java 层（也让 H2 和 MySQL 行为一致）

### 12.1 结构性降重（最有效）
| 章节 | 传统写法（易重复） | 本项目写法（低重复） |

### 12.2 语言层去 AI 味（写作时执行）
**禁用清单**：首先/其次/再次/最后、综上所述、总而言之、值得注意的是、不仅…而且…、赋能、闭环、抓手、多维度、显著提升、极大地、有效地、旨在、随着…的不断发展。
**句式要求**：长短句交错，允许出现"这里踩了个坑""一开始想的是…后来发现不行"这类口语化工程叙述；段落长短不齐（别每段都 3 行）；适当用"笔者"。
**内容要求**：每 500 字至少要有一个**具体到不可编造**的细节——具体版本号、具体报错信息、具体耗时数字、具体表字段名、具体测试数据（如"并发 50 时，旧方案出现 3 次超卖"）。

### 12.3 图表与代码
- 所有图用 draw.io / Visio / Excel 手绘，**不用 AI 生成**（AI 图的线条和字体特征明显）
- 截图用真实系统，含真实中文数据（张三、李四改成"2023 级计算机 2 班 王雨桐"这类）
- 代码注释自己写，变量名贴业务（`signupDeadline`、`checkinCode`），删掉 AI 式的"// 这里进行参数校验"整段注释
- 关键算法手写：并发扣减、签到码生成、质量分公式，并在论文里贴出你的推导过程

### 12.4 目标线
- 知网查重：< 15%（学校一般要求 30% 以内，留足余量）
- AIGC 检测：< 20%
- 自检工具：知网小分解 / PaperYY / 维普，定稿前跑 2 轮

### 12.5 按知网标准执行的细则（已确定查重系统为知网）

知网的判定规则和别的系统不一样，针对性地写才有效：

| 知网规则 | 对写作的直接影响 |
|---|---|
| **连续 13 个字符与库中文献相同即标红** | 不要整句照搬定义，哪怕只改几个词也照样红。技术定义必须用自己的话重述 |
| **标红按"段"计算重复率** | 一段里有一句重复，整段都会被重点关注；短段落更安全 |
| **引用必须按 GB/T 7714 规范标注，否则引用内容计入重复率** | 参考别人的观点一定加 `[1]` 上标，正文和文末参考文献一一对应 |
| **目录、参考文献、致谢参与检测** | 模板化的致谢最容易红（"感谢导师的悉心指导"这类句子库里全是） |
| **AIGC 检测按段落给疑似度** | 一段之内句式太整齐、连接词太密集，疑似度会明显拉高 |

具体执行：

1. **技术章节（第 2 章）** 每段控制在 150~200 字，一段只讲一件事；框架介绍一律改写为"本项目为什么要用它"，避免出现"Spring Boot 是由 Pivotal 团队提供的全新框架"这种教科书句式
2. **需求分析（第 3 章）** 用本校真实调研数据，这一段几乎不可能重复；调研问卷的统计结论要带具体百分比和样本量
3. **系统设计（第 4 章）** 表结构、索引、接口清单都是自己产出的，天然零重复，可以多写
4. **系统实现（第 5 章）** 代码块和截图不重复，但解释性文字容易写成通稿，要用"问题—排查—解决"的具体过程来写
5. **致谢** 自己写具体的人和事，别套模板；这一段查重翻车率极高
6. **查重前处理**：删掉文档里所有 AI 生成痕迹的过渡句；把长句拆成短句；每 3~4 段插入一个只有你的项目才有的细节（字段名、报错信息、测试数字）

> 目标线定在 **< 15%**，比学校要求留出一倍余量。做到这个程度，即使不同系统检测口径有差异也稳。

### 踩坑记录（可直接写进论文 5.x）
1. Spring Boot 2.7.18 的依赖管理里 `mysql:mysql-connector-java` 已经没有版本号约束，必须显式写 `8.0.33`，否则 Maven 报 `'dependencies.dependency.version' is missing`
