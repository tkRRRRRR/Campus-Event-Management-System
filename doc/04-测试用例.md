# 校园活动管理系统 测试用例与测试记录

> 本文档是论文第 6 章（系统测试）的素材来源，也是答辩时"你到底测了什么"的直接证据。
> 所有用例均在本地 H2 演示库与云端 MySQL 8.4 两套环境上各跑过一遍，结果一致。

## 1. 测试环境

| 项目 | 配置 |
|---|---|
| 操作系统 | Windows 11（本地） / Linux（Render 容器） |
| JDK | 1.8.0_512（本地 tools/jdk8） |
| 应用 | Spring Boot 2.7.18，可执行 jar |
| 数据库 A | H2 1.4.200 内存库（演示模式，profile=h2） |
| 数据库 B | MySQL 8.4.3（SQLPub 云端） |
| 浏览器 | Chrome 120 / Edge 120 |
| 接口测试工具 | PowerShell Invoke-WebRequest 脚本（scripts/*.ps1）+ curl |
| 并发测试工具 | 自研 scripts/ConcurrencyTest.java（JDK 自带 HttpURLConnection + CountDownLatch） |

## 2. 测试方法

1. **功能测试**：按角色（学生 / 组织者 / 管理员）逐条走业务流程，使用等价类与边界值设计用例。
2. **接口测试**：用脚本对每个接口做正向与反向断言（状态码 + 业务码 + 提示语），共 4 个脚本、约 90 条断言。
3. **并发测试**：50 个线程同时对容量 10 的活动发起报名，对比"数据库原子扣减"与"先查后改"两种实现的超卖情况。
4. **权限测试**：用学生 token 调用组织者/管理员接口，验证 403；不带 token 验证 401；伪造 token 验证 401。
5. **部署测试**：单 jar + 便携 JRE 拷贝到另一台未装 Java 的电脑运行；Vercel + Render 在线访问。

## 4. 并发测试（重点）

### 4.1 测试设计

- 目标活动：capacity=10，状态=报名中，无需审核
- 并发用户：50 个学生账号（2023010200~2023010249），密码统一 123456
- 同步方式：`CountDownLatch` 让 50 个线程同时阻塞，主线程 `countDown()` 后同时发起 POST /api/registration/{activityId}
- 统计方式：解析响应 msg 分类计数；压测后用详情接口核对 `signedCount` 与 `joinedCount`

### 4.2 对照组：先查后改（`--app.registration.naive=true`）

```java
// 错误示范：先查后改，两步之间没有原子性
Integer signed = activity.getSignedCount();
if (signed >= activity.getCapacity()) { throw new BusinessException("名额已满"); }
activity.setSignedCount(signed + 1);
activityMapper.updateById(activity);   // 丢失更新
Thread.sleep(20);                      // 实验用，放大竞态窗口
```

| 指标 | 结果 |
|---|---|
| 耗时 | 212 ms |
| 报名成功 | **50 人**（容量只有 10） |
| 提示"名额已满" | 0 人 |
| signedCount（冗余计数） | **6** |
| joinedCount（真实明细） | **50** |
| 结论 | 超卖 40 人，且冗余计数因丢失更新只剩 6，与明细完全不一致 |

### 4.3 实验组：数据库原子扣减（默认实现）

```sql
update activity
   set signed_count = signed_count + 1
 where id = #{activityId}
   and signed_count < capacity
   and status = 2
```

仅当影响行数 == 1 时才写入报名记录；影响行数为 0 则回滚并返回"名额已满"。

| 指标 | 结果 |
|---|---|
| 耗时 | 77 ms |
| 报名成功 | 10 人 |
| 提示"名额已满" | 40 人 |
| signedCount | 10 |
| joinedCount | 10 |
| 结论 | 无超卖，冗余计数与明细严格一致 |

### 4.4 结论

在同一个 JVM、同一张表、同样 50 并发下，"先查后改"出现 40 人超卖，而"单条 UPDATE 带条件"实现零超卖且耗时更短（77 ms vs 212 ms，因为省去一次查询与人为 sleep）。这验证了：把"判断"与"扣减"合并进一条 SQL 是解决超卖最简单可靠的手段，不需要引入分布式锁或 Redis。
