# 答辩问答准备（21 问）

> 用法：不必背全文，记住每问的**第一句**和**一个数字**。回答控制在 4 句以内，先说结论，再说依据，最后补一句边界或不足，比长篇解释更稳。

## 一、方案选型类

**Q1 为什么不用 Spring Security，自己写拦截器是不是重复造轮子？**

这是权衡后的选择。Spring Security 的过滤器链、用户详情服务和异常处理都要改写成项目统一的返回格式，配置量不小；而本系统只需要"校验令牌 + 比对角色"两件事，自己写拦截器约一百多行，逻辑可读、便于调试。代价是缺少现成的会话管理、记住我等功能，密码加密用 Hutool 的 BCrypt 补上。如果系统要接入 OAuth2 或单点登录，我会换成 Spring Security。

**Q2 为什么不用 Redis 或分布式锁？**

因为当前是单库、单实例，名额扣减用数据库条件更新就能保证原子性，Redis 属于为解决不存在的问题引入组件。引入后还要处理锁超时、锁误删、Redis 与数据库不一致等新问题，反而增加出错面。如果将来多实例部署且必须限制全局速率，才会考虑 Redis。

**Q3 为什么不用乐观锁（version 字段）？**

乐观锁也能解决超卖：更新时带上版本号，失败重试。区别在失败成本——抢名额时大量请求会失败重试，重试次数随并发上升，而条件更新一次 SQL 就能判定成功或失败，不需要重试循环。另外乐观锁需要给活动表加版本字段并维护，条件更新利用的是已有的 capacity 和 signed_count，改动更小。

**Q4 为什么用 MyBatis-Plus 而不是 JPA？**

主要是 SQL 可控。报名名单、统计聚合、排行榜这类多表查询，JPA 要么写原生 SQL 要么绕很大一圈，而 MyBatis-Plus 单表用 Wrapper、复杂查询写 XML，两种都能落在一个文件里，便于对照论文讲解。分页插件也能直接给出总数，省去手写 count 语句。

**Q5 前端为什么用 Vue 2 和 hash 路由，不用 Vue 3？**

Vue 2 是因为 Element UI 只支持 Vue 2，而 Element Plus 这两年的组件 API 变动较多，一个人写 19 个页面，稳定优先。hash 路由是为了静态托管省事：打包产物放进 jar 或任意子目录都能直接访问，不需要服务器配置 URL 重写。

**Q6 为什么选 Spring Boot 2.7 而不是 3.x？**

因为 3.x 要求 JDK 17，而机房和同学电脑上多数是 JDK 8。答辩现场如果因为环境打不开，损失比用新版本更大。2.7 是 2.x 的最后一个分支，资料多、问题容易查到。

## 二、并发与数据一致性类

**Q7 50 并发这个数字是怎么来的，可信吗？**

用自己写的 Java 程序跑的，不依赖第三方库：先串行登录 50 个学生账号拿到令牌，再用 CountDownLatch 让 50 个线程同时起跑，最后用活动详情接口核对计数。容量设为 10，测试前后数据库状态可控，结果可重复。要说局限，它是在单机内存库上跑的，没有覆盖多实例和网络抖动。

**Q8 如果并发到几千，条件更新还成立吗？**

正确性成立，性能会下降。因为同一行上的更新会排队等行锁，并发越高，等待越明显，接口响应时间会上升。此时的优化方向不是换锁，而是把热点拆开，例如按名额分桶、排队发号，或者把报名改成异步队列削峰。这些属于规模化改造，超出了本文范围。

**Q9 signed_count 是冗余字段，会不会和明细不一致？**

正常流程下不会：名额扣减和明细插入在同一个事务里，任何一步失败都回滚。系统里还有两处兜底——数据库的唯一索引防止重复报名，测试脚本每次操作后会比对计数与明细。但需要承认，手工改数据库或直接写 SQL 可能破坏一致性，所以生产环境应禁止绕过接口修改这两张表。

**Q10 取消报名后名额怎么还回去？**

取消时先判断记录状态是已报名或待审核、且活动尚未开始，然后把记录置为已取消，同时对活动执行 signed_count 减一，两者在同一事务中。爽约不归还名额，因为爽约者占用了名额却没有到场，归还反而让统计失真。

## 三、安全类

**Q11 JWT 签发后不能注销，这个问题怎么办？**

这是 JWT 的固有特性，我在论文里把它列为不足。目前的弥补是两点：登录时校验账号状态，被禁用账号直接拒绝；报名时校验限制时间，被封禁用户即使拿着有效令牌也报不了名。真正的即时失效可以给用户加一个令牌版本号，改密码或禁用时递增，拦截器比对版本号即可。

**Q12 密码是怎么存的？盐值呢？**

用 BCrypt 存储，每次加密自动生成随机盐，盐值包含在结果字符串里，校验时不需要单独取盐。数据库里看不到明文，也无法通过两次相同密码判断是否同一个人——相同密码的哈希结果不同。

**Q13 怎么防止横向越权，比如学生 A 取消学生 B 的报名？**

两层控制。接口层用角色注解限制"谁能调这个接口"，数据层再校验"这条记录是不是你的"：取消报名时用当前登录用户的 ID 作为查询条件，查不到就返回 404；组织者查看名单时校验活动归属；管理员操作自己也受限，例如不能禁用自己、不能把自己降级成最后一个管理员之外的角色。

**Q14 6 位签到码会不会被暴力猜？**

有概率，但成本不低：签到码只对已报名该活动的学生有意义，未报名者即使猜中也只会得到"你没有报名该活动"；同一活动 30 分钟内有效，且组织者可重新生成；接口层有登录校验，未登录无法调用。如果要更严格，可以加尝试次数限制或改成动态二维码，这些在展望里提过。

## 四、工程与测试类

**Q15 H2 和 MySQL 两套库，怎么保证 SQL 都能跑？**

建表脚本只用公共子集：不写 ENGINE、COMMENT 和内联 KEY，字段类型限制在两边都支持的范围；索引单独放在 MySQL 脚本里，因为 H2 不认那套写法。H2 用 MODE=MySQL 启动，并开启 DATABASE_TO_LOWER 保证大小写一致。日期聚合没有写在 SQL 里，而是把时间列查出来在 Java 层按日期归并，绕开两边的函数差异。

**Q16 统计接口每次都实时聚合，性能怎么考虑？**

当前数据量下（74 用户、239 条报名）响应在几十毫秒，够用。设计上把聚合放在数据库，Java 层只做日期补齐和权重计算。数据量上来后的方案是按天预聚合到统计表，接口只读结果，或者对概览加短时缓存；这一点在论文不足里写了。

**Q17 为什么测试用脚本，不用 JUnit？**

两个原因：一是接口级测试更接近真实调用，脚本直接发 HTTP 请求，带令牌、带 JSON，能覆盖拦截器和参数校验；二是这些脚本答辩时还能复用，现场演示前跑一遍就知道系统是否正常。JUnit 更适合单元测试，后续可以补上服务层的单元测试。

**Q18 部署为什么没有真正上线？**

原计划前端放 Vercel、后端放 Render，配置和 Dockerfile 都写好了，也验证了连云端 MySQL 8.4 能正常读写。没有实际部署的原因是时间与账号限制：Render 免费实例会休眠，首次访问要等几十秒，答辩现场不可控；而 Vercel 默认域名在国内访问不稳定。所以现场用便携包，云端形态作为配置说明保留。

## 五、综合类

**Q19 与已有的校园活动系统相比，你的工作亮点在哪？**

两点。一是把报名名额的并发控制做成可验证的实验：不只是说用了原子更新，而是给出 50 并发下的对照数据，说明"先查后改"会超卖 40 人、计数还会失真。二是签到不只做码，而是把码的有效期、签到时间窗口、爽约累计和补签纠错串成一条闭环，让"报名了不来"这件事有成本、也有纠错通道。

**Q20 系统还缺什么？**

四点：令牌无法主动失效；统计实时聚合，数据量大后需要预聚合；管理员操作没有审计日志；签到只有码的方式，缺少定位或扫码。这四点都在论文第 7 章列了改进方向，其中令牌版本号和操作日志工作量不大，可以优先补。

**Q21 这个系统是你独立完成的吗？哪些部分参考了别人的？**

系统是我独立完成的：数据库设计、后端 8 个模块、前端 19 个页面、测试脚本和便携包打包。参考主要集中在技术文档与同类论文的写法上，例如 Spring Boot、MyBatis-Plus 的官方文档，以及参考文献里几篇校园活动系统的设计与实现论文；论文中已按规范标注引用。开发过程中使用 AI 工具辅助排查报错和润色文字，代码逻辑与测试数据均由我本人验证。

## 六、答不上来时怎么办

- **完全不会**：不要沉默或编造。可以说"这个问题我目前没有深入研究，我的理解是……，回去我会补充验证"，然后把话题拉回你熟悉的相关点。
- **老师指出错误**：先接受，再说明影响范围。"您指出的这一点确实存在，在当前实现里会导致……，如果修改，我会从……入手。"不要辩解。
- **被追问细节**：只答你验证过的数字和代码位置，例如"这个逻辑在 `RegistrationServiceImpl` 的 register 方法里，校验顺序是先判断活动状态，再判断截止时间"。
- **被问到论文没写的**：承认边界，给方向。"论文里没有展开这一点，我的初步想法是……，但这需要进一步验证。"
