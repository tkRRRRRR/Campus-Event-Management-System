# 第3章 需求分析

## 3.1 角色分析

系统面向校园场景，使用者分为三类，权限逐级递增。

**学生**是系统的数量主体。其诉求集中在三件事：找到想参加的活动、顺利完成报名、活动结束后留下评价。学生不需要看到其他学生的手机号，也不需要知道活动的审核细节。

**组织者**通常是学生会或社团的负责人，负责一场或几场活动从发布到收尾的全过程。其核心诉求是把线下流程搬到线上：发出活动、控制名额、审核特殊报名、现场组织签到、事后看数据。

**管理员**站在平台视角，管的是规则而不是具体活动：审核活动内容是否合规、维护活动分类、管理系统用户、发布全站公告、配置违约阈值等平台参数。

三类角色的权限边界如表 3-1 所示。

| 功能 | 学生 | 组织者 | 管理员 |
| --- | --- | --- | --- |
| 浏览活动、查看详情 | √ | √ | √ |
| 报名、取消报名、签到 | √ | — | — |
| 评价已参加的活动 | √ | — | — |
| 发布活动、编辑、取消 | — | √（本人活动） | — |
| 查看报名名单、审核报名 | — | √（本人活动） | √ |
| 生成签到码、补签、结束活动 | — | √（本人活动） | √ |
| 审核活动、管理用户与分类 | — | — | √ |
| 查看平台级统计 | — | — | √ |

## 3.2 功能需求

按业务主线划分，系统需要实现以下功能。

**（1）用户与认证。** 学生凭学号注册，注册时填写姓名、学号、手机号；登录成功后获得令牌；支持修改个人资料、上传头像、修改密码；管理员可以按角色与关键字检索用户，禁用账号、调整角色、重置密码。

**（2）活动管理。** 组织者填写标题、分类、简介、详情、地点、起止时间、报名截止时间、名额、是否需要审核、封面图，保存为草稿或提交审核；提交后由管理员审核，驳回时必须填写理由；被驳回的活动可以修改后重新提交；活动开始前组织者可以取消活动，取消时需通知已报名学生。

**（3）活动浏览。** 学生按分类、关键字、排序方式（最新、最热）检索活动，分页浏览列表；详情页展示活动信息、剩余名额、报名截止倒计时、报名进度、签到人数、评分与评价列表。

**（4）报名管理。** 学生报名时系统依次校验活动状态、报名截止时间、是否已开始、是否被封禁、是否重复报名；名额未满才允许报名。需要审核的活动先进入待审核状态，不占用名额，组织者通过后才真正占位。学生可以取消报名，取消后名额归还。

**（5）签到管理。** 组织者生成 6 位签到码，签到码有有效期；学生在签到窗口内输入签到码完成签到；组织者可以查看签到名单、统计签到率、为个别学生补签；活动结束时系统判定未签到者为爽约，累计违约次数，超过阈值后限制其报名一段时间。

**（6）评价管理。** 活动结束后，实际参加（已签到）的学生可以对活动打分并写评价，一人一条；支持匿名评价；学生可以删除自己的评价；评价列表展示评分分布与平均分。

**（7）统计。** 平台维度统计用户数、活动数、报名数、签到率、评分等指标；组织者维度统计自己活动的情况；提供按天的报名与签到趋势、按分类的分布、按报名人数的活动排行。

**（8）通知与公告。** 活动审核结果、报名审核结果、爽约提醒、封禁通知等以站内消息形式发给对应用户；管理员发布的全站公告在首页轮播展示。

## 3.3 非功能需求

**易用性。** 主要操作不超过三步；表单给出明确的字段约束与错误提示；列表页支持分页与筛选；移动端浏览器可正常浏览，便于学生现场签到时用手机操作。

**性能。** 单场活动报名的瞬时并发按 200 人估算，接口响应时间应控制在 1 秒以内；列表与统计接口在演示数据规模下应低于 300 毫秒。

**正确性。** 报名人数不得超过名额上限；冗余计数字段与明细记录必须一致；签到只能成功一次；同一学生对同一活动只能有一条有效评价。

**安全性。** 密码加盐哈希存储；接口默认需要令牌；越权访问返回 403；组织者只能操作自己的活动；管理员不能禁用自己或降级最后一个管理员。

**可部署性。** 除标准部署外，需要提供无需安装数据库与 Java 环境的便携运行方式，便于答辩现场与更换电脑时使用。

## 3.4 业务流程

**报名流程。** 学生点击报名后，服务端按固定顺序校验：活动存在且处于报名中状态、当前时间未过报名截止、活动尚未开始、用户未被限制报名、无重复报名记录。校验通过后执行名额扣减：若活动需审核，先写一条待审核记录；否则直接执行条件更新，影响行数为 1 表示占位成功，为 0 表示名额已满并返回提示。

**签到流程。** 组织者在活动开始前生成签到码，系统记录生成时间与过期时间，有效期默认 30 分钟且不晚于活动结束时间。学生在签到窗口内向接口提交签到码，服务端校验码值、有效期、报名状态，通过后将报名记录置为已签到并写入签到时间与签到方式。活动结束时，组织者手动结束或定时任务自动结束，系统把仍未签到的报名记录置为爽约，并累加违约次数。

**评价流程。** 学生进入已结束且自己已签到的活动，在详情页提交评分与文字评价。服务端校验活动状态、报名状态、是否已评价，通过后写入评价记录。匿名评价在服务端脱敏，非本人与非管理员看到的用户名统一为"匿名同学"。

# 第4章 系统设计

## 4.1 总体架构

系统采用前后端分离的三层结构，如图 4-1 所示。

![图 4-1 系统总体架构](figures/fig-arch.png)

前端是 Vue 单页应用，通过 axios 调用后端 REST 接口，令牌放在请求头中。后端按职责划分为控制层、业务层与数据层：控制层负责参数接收与结果包装，业务层承担校验、事务与状态流转，数据层由 MyBatis-Plus 的 Mapper 与 XML 组成。横向上有拦截器负责鉴权，全局异常处理器负责错误归一，定时任务负责活动状态推进。

部署时前端构建产物被放入后端 `src/main/resources/static` 目录，与后端一起打成可执行 jar，因此生产环境只有一个进程、一个端口，不存在跨域问题。开发阶段前端单独运行在 8081 端口，通过 devServer 代理访问 8080 的后端。

## 4.2 功能模块设计

系统划分为 8 个模块，如图 4-2 所示。

![图 4-2 功能模块结构](figures/fig-modules.png)

模块之间通过服务接口调用，不直接访问对方的 Mapper。例如报名模块在扣减名额时调用活动模块提供的原子更新方法，签到模块在判定爽约时调用报名模块的批量状态更新方法。这样做的目的是让"谁拥有数据谁负责写"这条规则在代码层面可检查。

## 4.3 数据库设计

### 4.3.1 概念结构

系统共 8 张表：用户表、活动分类表、活动表、报名表、评价表、个人消息表、平台公告表、系统参数表。实体之间的关系如图 4-3 所示。

![图 4-3 系统 E-R 图](figures/fig-er.png)

一名用户可以发布多个活动（组织者），可以有多条报名记录，可以有多条评价；一个活动属于一个分类，拥有多条报名与多条评价；报名记录是用户与活动之间的关联实体，同时承载签到状态、签到时间、签到方式等属性。

### 4.3.2 逻辑结构

受篇幅限制，此处只列出关键表的主要字段，完整建表语句见项目 `db/schema.sql`。

**用户表 sys_user**：主键 id，学号/工号 username（唯一），密码 password（BCrypt 哈希），姓名 real_name，角色 role（STUDENT/ORGANIZER/ADMIN），手机号 phone，邮箱 email，头像 avatar，状态 status（1 正常、0 禁用），违约次数 violation_count，限制截止时间 ban_until，创建时间 create_time。

**活动表 activity**：主键 id，标题 title，分类 category_id，简介 summary，详情 content，封面 cover_url，地点 location，开始与结束时间 start_time、end_time，报名截止 signup_deadline，名额 capacity，已占名额 signed_count，是否需要审核 need_audit，状态 status，审核备注 audit_remark，组织者 organizer_id，浏览量 view_count，创建时间 create_time。

**报名表 activity_registration**：主键 id，活动 activity_id，用户 user_id，状态 status（1 已报名、2 已签到、3 已取消、4 爽约、5 待审核），报名时间 signup_time，签到时间 checkin_time，签到方式 checkin_type（1 签到码、2 补签）。活动与用户组合建立唯一索引，从数据库层面杜绝重复报名。

**评价表 activity_review**：主键 id，活动 activity_id，用户 user_id，评分 score（1—5），内容 content，是否匿名 anonymous，创建时间 create_time。活动与用户组合唯一。

**其他表**：活动分类表保存分类名称、排序与启用状态；个人消息表保存接收人、类型、标题、内容与已读标记；平台公告表保存标题、正文、发布人与发布状态；系统参数表以键值对形式保存违约阈值、封禁天数、签到码有效期、默认名额等可配置项。

### 4.3.3 索引设计

除主键外，报名表在 `activity_id`、`user_id` 上建立索引，支撑"查我的报名"和"查活动名单"两个高频查询；活动表在 `status`、`category_id`、`organizer_id` 上建立索引，支撑列表筛选与组织者的活动列表；消息表在 `user_id` 与 `is_read` 上建立索引，支撑未读数统计。索引脚本单独放在 `db/indexes.sql` 中，因为 H2 不支持部分 MySQL 索引语法。

## 4.4 关键机制设计

### 4.4.1 名额原子扣减

名额扣减是整个系统最需要保证正确性的地方。设计上把"判断"和"修改"合并到一条 SQL 中：

```sql
update activity
   set signed_count = signed_count + 1
 where id = #{activityId}
   and signed_count < capacity
   and status = 2
```

业务层根据返回的影响行数判断结果：等于 1 表示占用成功，等于 0 表示名额已满或活动状态已变化，抛出业务异常并回滚本次报名。由于条件判断与自增在同一条语句内完成，并发请求会在行锁上排队，不会出现两个请求同时通过判断的情况。

这条语句同时承担了活动状态校验：`status = 2` 保证只有处于报名中的活动能被报名。取消报名时执行反向更新 `signed_count = signed_count - 1 where id = ? and signed_count > 0`，取消与归还在同一条语句内完成，避免归还后计数为负。

需要说明的是，唯一索引负责防重复报名，条件更新负责防超卖，二者分工不同。若只依赖唯一索引，虽然同一用户不会重复报名，但不同用户仍可能同时挤入最后几个名额；若只依赖条件更新，同一用户并发点击两次可能占用两个名额。

### 4.4.2 签到码与爽约限制

签到码为 6 位数字，由 `ThreadLocalRandom` 生成，拼装时保证不以 0 开头（以 0 开头的码在部分输入法下容易被吞掉）。生成时若存在未过期的旧码则直接复用，避免组织者反复点击导致码变化、学生手里的码失效。

签到窗口设为"活动开始前 30 分钟至活动结束"，这样既覆盖了提前到场排队的时间，也避免活动结束后补签演变成常态。补签由组织者手工操作，会记录签到方式以便统计。

爽约判定在活动结束时统一执行：取出该活动所有状态为"已报名"的记录，批量置为"爽约"，同时给每个用户累加违约次数；违约次数达到阈值（默认 2 次）时，把 `ban_until` 设为当前时间加封禁天数（默认 30 天），并发送通知。被限制的用户在报名时会被拦截，提示限制截止日期。

### 4.4.3 活动质量分

为了让学生快速判断一场活动是否值得参加，系统为每个活动计算质量分：

```
质量分 = 签到率 × 40 + 评分归一化 × 40 + 完成率 × 20
```

其中签到率为已签到人数与应到人数之比，评分归一化为平均分除以 5，完成率为已结束活动取 1、未结束按时间进度折算。三项权重体现的假设是：到场率最能反映活动的真实吸引力，评分反映满意度，完成率则对尚未结束的活动给出保守估计。

质量分在查询详情时实时计算，不落库。原因是活动进行中各项指标持续变化，落库需要频繁更新，反而增加复杂度；该计算只涉及几个整数与一次除法，开销可以忽略。

### 4.4.4 权限设计

权限分两层。第一层是接口级：`@RequireRole` 注解声明允许的角色，拦截器比对当前用户角色，不匹配返回 403。第二层是数据级：组织者只能操作自己的活动，业务层在更新、取消、审核报名等操作前调用统一的归属校验方法，比较活动或报名的 `organizer_id` 与当前用户；管理员跳过归属校验。

数据级校验必须在服务端完成。前端虽然会根据角色隐藏入口，但接口可以被直接调用，仅靠前端控制等同于没有控制。系统在管理员登录时不再展示组织者菜单，正是为了避免管理员点进去后被 403 拦住这种体验问题。

## 4.5 接口设计

接口遵循 REST 风格，统一前缀 `/api`，统一返回 `{code, msg, data}`。成功时 `code` 为 200；参数错误为 400，未登录为 401，无权限为 403，资源不存在为 404，系统异常为 500。分页接口统一接收 `pageNum` 与 `pageSize`，返回 `{pageNum, pageSize, total, records}`。

接口按资源划分：认证 `/api/auth/*`、用户 `/api/user/*`、分类 `/api/category/*`、活动 `/api/activity/*`、报名 `/api/registration/*`、签到 `/api/checkin/*`、评价 `/api/review/*`、统计 `/api/stat/*`、通知 `/api/notice/*`、公告 `/api/announcement/*`、参数 `/api/config/*`。完整的接口清单与字段说明见项目文档 `doc/02-接口文档.md`。

设计过程中做了两点取舍。其一是"列表接口不返回大字段"：活动详情正文可能上千字，列表只返回标题、封面、时间、地点与报名情况，避免一次查询传输几十 KB 的文本。其二是"统计接口不接受前端传入的组织者 ID"：组织者维度的统计由服务端根据令牌中的用户身份确定范围，防止通过改参数查看他人的数据。
