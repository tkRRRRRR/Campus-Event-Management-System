# 第3章 需求分析

## 3.1 角色分析

系统的角色划分依据活动组织过程中的实际分工，而非界面菜单的差异。三类角色承担不同职责，权限边界由业务规则确定。

**学生**是系统的主要使用者。其需求集中在三个方面：获取活动信息、确认名额并完成报名、在活动当天完成签到；活动结束后，还需能够对参与的活动作出评价。学生之间不存在信息共享需求，因此系统不向学生展示其他报名者的联系方式，活动被驳回的具体理由属于组织者与管理员之间的沟通内容，同样不对学生展示。

**组织者**承担单场活动的具体组织工作，包括活动发布、名额控制、报名审核、现场签到管理与活动数据查看。组织者不具备活动审核权限，活动审核统一由管理员执行，以避免发布与把关由同一角色承担。

**管理员**负责平台层面的规则维护，包括活动审核、分类维护、账号管理、公告发布与系统参数配置。管理员不发布活动、不参与报名，以保证审核与执行相互独立。

三类角色的功能权限如表 3-1 所示。

| 功能 | 学生 | 组织者 | 管理员 |
| --- | --- | --- | --- |
| 浏览活动、查看详情 | √ | √ | √ |
| 报名、取消报名、签到 | √ | — | — |
| 评价已参加的活动 | √ | — | — |
| 发布活动、编辑、取消 | — | √（本人活动） | — |
| 查看报名名单、审核报名 | — | √（本人活动） | √ |
| 生成签到码、补签、结束活动 | — | √（本人活动） | √ |
| 审核活动、管理用户与分类 | — | — | √ |
| 查看平台级统计 | — | — | √ |

表 3-1 中的“本人活动”为数据级约束，而非界面层面的入口隐藏。系统在涉及活动或报名记录的写操作中，均比对记录中的组织者标识与当前登录用户标识，不匹配则拒绝执行，管理员除外。

## 3.2 功能需求

系统按业务主线划分为八项功能。以下分别说明功能内容、规则依据与边界条件。

**（1）用户与认证。** 学生以学号注册，填写姓名、学号与手机号，密码长度不少于 6 位；登录成功后获得访问令牌，后续请求均需携带令牌。个人中心支持资料修改、头像上传与密码修改；管理员可按角色与关键字检索用户，并执行禁用账号、调整角色与重置密码操作。边界条件包括：管理员不得禁用自己的账号，也不得将最后一个可用管理员降级，以保证平台始终存在管理入口；修改密码时新旧密码不得相同，以避免误操作。

**（2）活动管理。** 组织者填写标题、分类、简介、详情、地点、起止时间、报名截止时间、名额、是否需要报名审核与封面图，可保存为草稿或直接提交审核。活动提交后进入待审核状态；管理员驳回时须填写理由，组织者据此修改后可重新提交。活动开始前，组织者可以取消活动，系统向已报名学生逐条发送站内消息。边界条件包括：报名截止时间必须早于活动开始时间；活动开始后不可取消、不可编辑；待审核状态允许编辑，修改后需重新审核。

**（3）活动浏览。** 学生可按分类、关键字与排序方式（最新、最热）浏览活动列表，列表分页展示；详情页展示活动信息、剩余名额、报名截止倒计时、报名进度、签到人数、评分与评价列表。为控制传输数据量，列表接口不返回活动正文，仅返回标题、封面、时间、地点与报名情况。

**（4）报名管理。** 报名时服务端按固定顺序校验：活动存在且处于报名中状态、当前时间未过报名截止时间、活动尚未开始、账号未被限制报名、不存在重复的有效报名记录。全部通过后扣减名额。需审核的活动先写入待审核记录，此时不占用名额；组织者审核通过时才执行名额扣减，若名额已满则返回“名额已满，无法通过该报名”。学生可取消报名，取消已占用名额的记录时系统归还名额；已取消的记录不删除，再次报名时复用原记录，避免产生冗余历史数据。

**（5）签到管理。** 组织者生成 6 位签到码，签到码具有有效期，默认 30 分钟，且不晚于活动结束时间；学生在活动开始前 30 分钟至活动结束的时间窗口内输入签到码完成签到。组织者可查看签到名单与签到率，并为个别学生补签。活动结束时，仍未签到的报名记录判定为爽约，累加违约次数；达到阈值时限制报名一段时间。边界条件包括：签到码在有效期内重复生成时返回同一码值，避免学生已获取的签到码失效；补签会回退一次违约次数，若回退后低于阈值，则解除报名限制。

**（6）评价管理。** 活动结束且本人已签到的学生方可评价，评价内容为 1 至 5 星评分与文字说明，每人对同一活动仅可评价一次。系统支持匿名评价，匿名处理在服务端完成，非本人与非管理员查看时统一显示为“匿名同学”。学生可删除本人评价，管理员可删除任意评价。未签到者即使已报名也不可评价，该规则将评价与真实到场关联。

**（7）统计。** 统计分为平台与组织者两个视角。平台视角统计用户数、活动数、报名数、签到率与评分；组织者视角统计本人发布活动的情况。两者均可查看按日期的报名与签到趋势、按分类的分布以及按报名人数的排行。统计范围由访问令牌决定，不接受前端传入的组织者标识，防止越权查询。

**（8）通知与公告。** 审核结果、报名审核结果、爽约提醒与封禁通知以站内消息形式发送给指定用户；管理员发布的全站公告在首页展示。个人消息仅查询当前用户的相关记录，公告为全局数据，两者分表存储，避免已读状态被共享。

## 3.3 非功能需求

**易用性。** 常用操作不超过三步；表单提供字段约束与具体的错误提示，例如报名截止时间校验失败时返回“报名截止时间不能晚于活动开始时间”，而不是笼统的参数错误提示；列表支持筛选与分页；页面在 768 像素以下切换为移动端布局：侧边栏收起为抽屉，学生角色显示底部四个入口，表格类列表改为卡片，表单与弹窗占满宽度，按钮与输入框高度不小于 36 像素，以保证单手操作与现场签到时的可用性。

**性能。** 按单场活动 200 人同时报名的规模估算，报名接口响应时间应控制在 1 秒以内；在演示数据规模下，列表与统计接口响应时间应低于 300 毫秒。

**正确性。** 报名人数不得超过名额；报名计数字段须与明细记录一致；同一学生对同一活动只能存在一条有效报名与一条评价；签到操作只能成功一次。上述约束在测试用例中逐项覆盖。

**安全性。** 密码采用 BCrypt 加盐哈希存储，不保存明文；接口默认需要令牌，白名单仅包含登录、注册与健康检查；越权访问返回 403；组织者仅能操作本人发布的活动；管理员不得禁用本人账号或降级最后一个可用管理员。

**可部署性。** 除常规部署方式外，系统应支持在未安装数据库与 Java 运行环境的情况下直接运行，以满足答辩现场更换设备时的演示需求。该需求决定了系统采用前端资源打包进可执行 JAR、并内置 Java 运行环境的交付方式。

## 3.4 业务流程

**报名流程。** 学生提交报名请求后，服务端依次判断：活动是否存在且状态为报名中；当前时间是否未过报名截止时间；当前时间是否早于活动开始时间；账号是否处于报名限制期；是否存在状态为已报名、已签到或待审核的记录。状态为爽约的记录同样拒绝报名，状态为已取消的记录则复用。校验全部通过后，若活动需要报名审核，写入状态为待审核的记录并返回提交成功；否则执行条件更新扣减名额，影响行数为 1 表示占位成功，为 0 表示名额已满或活动状态已变更，此时抛出业务异常并回滚本次操作。

**签到流程。** 组织者获取签到码时，若存在未过期且未超过活动结束时间的签到码，直接返回该码；否则生成新码并记录过期时间。学生提交签到码后，服务端校验码值、有效期、签到时间窗口与报名状态，通过后将报名状态由已报名改为已签到，并记录签到时间与签到方式。活动结束（手动结束或定时任务触发）时，将仍处于已报名状态的记录批量置为爽约，逐个累加违约次数，达到阈值时写入报名限制截止时间并发送通知。

**评价流程。** 学生在已结束的活动详情页提交评分。服务端校验活动状态为已结束、本人报名状态为已签到且尚未评价，通过后写入评价记录。匿名标记仅影响展示，数据库仍保留真实用户标识，便于管理员处理恶意评价。

# 第4章 系统设计

## 4.1 总体架构

系统采用前后端分离的三层结构，如图 4-1 所示。

![图 4-1 系统总体架构](figures/fig-arch.png)

前端为 Vue 单页应用，通过 Axios 调用后端接口，访问令牌置于请求头。后端按职责划分为三层：控制层负责参数接收与结果封装，业务层承担校验、事务与状态流转，数据层由 MyBatis-Plus 的 Mapper 与少量 XML 映射组成。此外，系统设置了若干公共设施：拦截器负责身份认证与角色校验，全局异常处理器将各类异常统一为同一返回结构，定时任务负责推进活动状态，静态资源映射使前端资源与上传的封面图可通过同一端口访问。

部署形态上，前端构建产物放置于 `src/main/resources/static` 目录，与后端一同打包为可执行 JAR，运行时为单一进程与单一端口，不存在跨域问题。开发阶段前端单独运行于 8081 端口，通过开发服务器将 `/api` 与 `/upload` 代理至后端 8080 端口，修改页面无需重启后端服务。

该方式的代价是前后端在发布环节存在耦合，前端变更后需重新打包。为此，系统提供构建脚本，将前端构建、产物复制与后端打包串联为一条命令，降低了重复操作成本。

## 4.2 功能模块设计

系统划分为 8 个功能模块，如图 4-2 所示。

![图 4-2 功能模块结构](figures/fig-modules.png)

模块之间通过服务接口调用，不直接访问其他模块的数据访问层。例如报名模块扣减名额时，调用活动模块提供的原子更新方法；签到模块判定爽约时，调用报名模块的批量更新方法。该约束使“数据由其所属模块负责写入”的原则在代码层面可被检查。若出现某模块直接修改其他模块数据表的情况，通常意味着状态流转的职责划分存在偏差。

## 4.3 数据库设计

### 4.3.1 概念结构

系统共设计 8 张数据表：用户表、活动分类表、活动表、报名表、评价表、个人消息表、平台公告表与系统参数表。实体关系如图 4-3 所示。

![图 4-3 系统 E-R 图](figures/fig-er.png)

一名组织者可以发布多个活动；一个活动属于一个分类，并对应多条报名与多条评价记录；一名学生可以存在多条报名与评价记录。报名表是用户与活动之间的关联实体，同时承载签到状态、签到时间与签到方式等仅对单次参与有效的属性，这些属性既不适合存放于活动表，也不适合存放于用户表。

### 4.3.2 逻辑结构

此处仅列出关键表的主要字段，完整建表语句见附录 B。

**用户表 sys_user**：主键 id，学号或工号 username（唯一），password（BCrypt 哈希值），real_name，role（STUDENT/ORGANIZER/ADMIN），phone，email，avatar，status（1 正常、0 禁用），violation_count，ban_until，create_time。

**活动表 activity**：主键 id，title，category_id，summary，content，cover_url，location，start_time，end_time，signup_deadline，capacity，signed_count，need_audit，status，audit_remark，organizer_id，view_count，create_time，以及签到码 checkin_code 与过期时间 code_expire_time。其中 `signed_count` 为冗余字段，表示已占用的名额，统计口径为状态为已报名、已签到与爽约的记录数；取消报名的记录会归还名额，爽约记录不归还，因其确实占用了参与名额。

**报名表 activity_registration**：主键 id，activity_id，user_id，status（1 已报名、2 已签到、3 已取消、4 爽约、5 待审核），signup_time，checkin_time，checkin_type（1 签到码、2 补签），并在 `(activity_id, user_id)` 上建立唯一索引。

**评价表 activity_review**：主键 id，activity_id，user_id，score（1 至 5），content，anonymous，create_time，同样在 `(activity_id, user_id)` 上建立唯一索引。

**其他表**：活动分类表保存名称、排序与启用状态；个人消息表保存接收人、类型、标题、内容与已读标记；平台公告表保存标题、正文、发布人与发布状态；系统参数表以键值对形式保存违约阈值、封禁天数、签到码有效期与默认名额。

两张唯一索引的作用不仅在于加速查询，更在于防止重复数据写入。应用层的重复校验在并发条件下可能同时通过，唯一索引可使第二条插入直接失败。系统将唯一键冲突异常统一转换为“操作重复，数据已存在”的业务提示。

### 4.3.3 索引设计

除主键索引外，报名表在 `activity_id` 与 `user_id` 上建立索引，分别支撑活动名单查询与个人报名查询；活动表在 `status`、`category_id` 与 `organizer_id` 上建立索引，支撑列表筛选、分类筛选与组织者活动列表；消息表在 `user_id` 与 `is_read` 上建立索引，支撑未读数量统计。索引脚本单独存放于 `db/indexes.sql`，因建表脚本需兼容 H2，而 H2 不支持 MySQL 的内联索引语法。

## 4.4 关键机制设计

### 4.4.1 名额原子扣减

名额分配是系统中对正确性要求最高的环节。设计上将容量判断与计数修改合并为一条语句：

```sql
update activity
   set signed_count = signed_count + 1
 where id = #{activityId}
   and signed_count < capacity
   and status = 2
```

业务层依据影响行数判断结果：行数为 1 表示占位成功，为 0 表示名额已满或活动状态已变更，此时抛出业务异常并回滚本次报名。由于判断与自增在同一语句内完成，并发请求在行锁上排队，不会出现两个请求同时通过判断的情况。

该语句同时承担状态校验，`status = 2` 保证仅处于报名中状态的活动可被报名，报名前仍会查询活动记录，用于完成截止时间、封禁状态等其余校验。取消报名时执行反向语句，将计数减一并附加 `signed_count > 0` 条件，防止计数为负。

唯一索引与条件更新承担不同的约束职责：唯一索引防止同一用户重复报名，条件更新防止不同用户同时占用最后若干名额。仅依靠前者无法避免超额报名，仅依靠后者则无法阻止同一用户重复占用名额。

需审核的活动为特例：报名时仅写入待审核记录，不占用名额；组织者审核通过时再执行同一条条件更新，若此时名额已满，则审核操作失败并提示“名额已满，无法通过该报名”。该处理方式避免了待审核记录长时间占用名额而导致其他学生无法报名的问题。

### 4.4.2 签到码与爽约限制

签到码由 6 位数字组成，采用 `String.format("%06d", ...)` 生成，可能包含前导零（例如 080021），因此前端按字符串处理，避免转换为数值后丢失前导零。生成签到码时先查询是否存在未过期的旧码，存在则复用，使有效期内重复获取得到同一码值，避免已发放的签到码失效。

签到窗口设置为活动开始前 30 分钟至活动结束。提前 30 分钟开放，便于学生到场后即时签到，窗口不延伸至活动结束后，以保证爽约判定的有效性。补签由组织者手工执行，调用独立接口，签到方式记为 2，与签到码签到区分统计。

爽约判定在活动结束时统一执行：查询该活动所有已报名记录，批量置为爽约状态，并将对应用户的违约次数加一；违约次数达到阈值（默认 2）时，将报名限制截止时间设置为当前时间加上封禁天数（默认 30 天），并发送报名受限通知；未达阈值的用户收到爽约提醒。补签时执行反向操作：记录恢复为已签到，违约次数减一，若减后低于阈值则清除报名限制。

该机制将缺席的代价由“无约束”转为“可能影响后续报名”，适用于校内活动场景，且无需额外的身份核验手段。

### 4.4.3 活动质量分

为便于比较活动效果，系统为每个活动计算质量分：

```
质量分 = 签到率 × w1 + 评分归一化 × w2 + 完成率 × w3
```

其中 w1、w2、w3 为三项权重，默认取 40、40、20，保存在系统参数中，管理员可在参数页调整。权重之和不必等于 100，计算时按 w1+w2+w3 归一化，因此改成 6、6、3 与 40、40、20 得到的分数相同，结果始终落在 0 至 100。

三项指标的定义如下：签到率为已签到人数与报名人数之比，反映报名者的实际到场比例；评分归一化为（平均分 − 1）/ 4，将 1 至 5 分的评分映射至 0 至 1 区间，无评价时按 0 计；完成率为 1 减去取消率，取消率为取消人数与（报名人数 + 取消人数）之比，反映报名后取消的比例。

默认权重的设置依据如下：签到率最能反映活动的实际吸引力，取权重 40；评分体现参与者满意度，取权重 40，但其样本量较小、波动较大，不宜赋予更高权重；完成率作为辅助指标，取权重 20。以某活动为例，80 人报名、60 人签到、平均分 4.2、无人取消，按默认权重得分为 0.75×40 + 0.8×40 + 1×20 = 82 分。

质量分在查询详情时实时计算，不写入数据库。原因在于活动进行期间各指标持续变化，持久化将带来频繁更新与数据同步问题，而该计算仅涉及少量整数运算与一次除法，开销可以忽略。

### 4.4.4 权限设计

权限控制分为接口级与数据级两层。接口级通过 `@RequireRole` 注解实现：在方法或类上声明允许访问的角色集合，拦截器将其与当前用户角色比对，不匹配时返回 403。数据级通过业务层的归属校验实现：组织者在更新或取消活动、查看名单、审核报名之前，系统均比对记录中的组织者标识与当前用户，管理员跳过该校验。

数据级校验必须在服务端执行。前端虽按角色隐藏入口，但接口可被直接调用，仅依赖前端控制等同于未设控制。基于同样的原因，管理员登录后不显示组织者菜单，因相关接口仅允许组织者访问，显示入口只会导致无效操作。

## 4.5 接口设计

接口遵循 REST 风格，统一前缀为 `/api`，统一返回结构为 `{code, msg, data}`。状态码约定为：成功 200，参数错误 400，未登录 401，无权限 403，资源不存在 404，系统异常 500。分页接口统一接收 `pageNum` 与 `pageSize` 参数，返回 `{pageNum, pageSize, total, records}` 结构。日期时间统一按 `yyyy-MM-dd HH:mm:ss` 格式序列化，避免前后端格式不一致。

接口按资源划分为：认证 `/api/auth/*`、用户 `/api/user/*`、分类 `/api/category/*`、活动 `/api/activity/*`、报名 `/api/registration/*`、签到 `/api/checkin/*`、评价 `/api/review/*`、统计 `/api/stat/*`、通知 `/api/notice/*`、公告 `/api/announcement/*`、参数 `/api/config/*`，共 60 个。完整清单与字段说明见项目 `doc/02-接口文档.md`。

设计中有三处取舍。第一，列表接口不返回活动正文等大字段，以降低传输与渲染开销。第二，统计接口不接受前端传入的组织者标识，统计范围由访问令牌确定。第三，签到码查询接口采用 GET 方法且仅执行读取，签到码生成必须通过 POST 方法完成，接口职责保持单一。
