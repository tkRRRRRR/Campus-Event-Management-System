# 第5章 系统实现

## 5.1 开发环境与项目结构

开发机配置为 Windows 11、16 GB 内存；JDK 1.8.0_512、Maven 3.9.9、Node.js 16.20.2；数据库为 MySQL 8.0（云端实例为 8.4）；前端依赖包括 Vue 2.7.16、Element UI 2.15.14、axios 1.6.8、ECharts 5.4.3、dayjs 1.11.10；后端依赖包括 Spring Boot 2.7.18、MyBatis-Plus 3.5.3.2、mysql-connector-j 8.0.33、H2 1.4.200、java-jwt 3.19.4、hutool 5.8.25、Lombok。

后端包名为 `com.campus.activity`，按职责分层：

```
controller   接口层，参数接收与结果包装
service      业务层，校验、事务与状态流转
  impl
mapper       数据访问层，通用方法与自定义 SQL
entity       与表一一对应的实体
dto          入参对象，承载校验注解
vo           出参对象，按页面需要裁剪字段
common       统一返回、业务异常、全局异常处理、常量
config       MyBatis-Plus、Jackson、WebMvc 配置
interceptor  JWT 拦截器
annotation   @RequireRole
task         定时任务
util         JWT 工具、当前用户上下文
```

入参与出参分离是本项目贯穿始终的约定。实体只用于数据库读写，接口从不直接返回实体，避免把密码、限制截止时间等内部字段暴露出去；也不同时用一个对象承担"接收"和"返回"两种职责，否则校验注解会互相干扰。

## 5.2 后端实现

### 5.2.1 认证与权限

登录接口接收用户名与密码，先用 `BCrypt.checkpw` 校验密码，再检查账号状态，通过后签发令牌。为避免暴力枚举时泄露账号是否存在，账号不存在与密码错误返回同一条提示"学号/工号或密码错误"。

拦截器实现 `preHandle`：从请求头取出令牌，校验签名与过期时间，解析出用户信息放入 `ThreadLocal`，随后读取处理方法上的 `@RequireRole` 注解做角色比对。`afterCompletion` 中调用 `UserContext.clear()`。这里有一个容易忽略的细节：Tomcat 的线程是复用的，如果不清理 `ThreadLocal`，下一个请求可能读到上一个用户的身份。

### 5.2.2 活动发布与审核

活动有六个状态：草稿、待审核、报名中、已驳回、已取消、已结束。状态流转集中在业务层，所有修改都先校验当前状态是否允许该操作。例如只有草稿、待审核、已驳回的活动可以编辑；只有待审核的活动可以审核；只有报名中的活动可以取消，且取消前会校验活动尚未开始。

发布时先做时间校验：开始时间必须晚于当前时间，报名截止不得晚于开始时间，结束时间必须晚于开始时间。校验失败给出具体提示，例如"报名截止时间不能晚于活动开始时间"，而不是笼统的"参数错误"。

审核接口接收通过与驳回两种结果，驳回时强制要求填写理由；理由写入活动记录，并通过消息表给组织者发一条通知。组织者在"我的活动"列表里能直接看到驳回理由，不必再点进详情。

取消活动时，系统查出所有有效报名记录，逐条发通知告知活动取消，再把报名记录置为已取消、名额清零。这一步用事务包住，避免通知发出而状态未改。

### 5.2.3 报名实现

报名是本系统的核心逻辑，代码约 120 行，按顺序完成五道校验后执行扣减，关键片段如下：

```java
// 1. 活动必须存在且处于报名中
Activity activity = activityMapper.selectById(activityId);
if (activity == null) throw new BusinessException("活动不存在");
if (activity.getStatus() != Constants.ACTIVITY_PUBLISHED)
    throw new BusinessException("该活动当前不可报名");
// 2. 报名截止与开始时间
if (LocalDateTime.now().isAfter(activity.getSignupDeadline()))
    throw new BusinessException("报名已截止");
if (LocalDateTime.now().isAfter(activity.getStartTime()))
    throw new BusinessException("活动已开始，无法报名");
// 3. 是否被限制报名
SysUser user = userMapper.selectById(userId);
if (user.getBanUntil() != null && user.getBanUntil().isAfter(LocalDateTime.now()))
    throw new BusinessException("因多次爽约，你被限制报名至 " + ...);
// 4. 是否重复报名
ActivityRegistration old = registrationMapper.selectOne(...);
if (old != null && old.getStatus() != Constants.REG_CANCELED)
    throw new BusinessException("你已报名该活动，请勿重复提交");
// 5. 命中名额
int affected = activityMapper.increaseSignedCount(activityId);
if (affected != 1) throw new BusinessException("名额已满，报名失败");
```

需要审核的活动走另一条分支：先插入一条状态为"待审核"的记录，此时不扣名额；组织者通过审核时再执行扣减，若此时名额已满则提示"名额已满，无法通过该报名"，并把记录保留为待审核状态，由组织者决定后续处理。这样设计的好处是名额只在确定占用时才扣，不会因为大量待审核申请而虚占名额。

取消报名只允许状态为"已报名"或"待审核"且活动尚未开始的记录，取消时若原本已占名额则归还。

### 5.2.4 签到实现

签到码的生成、查询、校验集中在签到服务中。生成时先查是否存在未过期且属于该活动的码，有则复用；否则生成新码并写入活动的 `checkin_code`、`checkin_code_expire` 字段（实际实现中复用了活动表的扩展字段，避免为此单建一张表）。有效期取配置的分钟数，并与活动结束时间取较小值。

学生签到时，服务端依次校验活动存在、签到码非空且有效、码值匹配、未过期、在签到窗口内、报名记录存在且状态为"已报名"、尚未签到，最后用条件更新 `set status = 2, checkin_time = now where id = ? and status = 1` 完成状态流转。使用条件更新而非先查后改，是为了防止学生连点两次导致重复签到。

组织者补签走另一个接口，直接按报名记录 ID 操作，允许把爽约记录改回已签到，同时把该用户的违约次数减一；若减后低于阈值，则清除限制截止时间。这一步是"给误判留出补救通道"的体现。

结束活动的接口会先取未签到的用户列表，批量置为爽约，再逐个累加违约次数与判断封禁，最后把活动状态改为已结束。接口返回爽约人数，前端据此给出"本次爽约 3 人"的具体提示。定时任务每 5 分钟扫描一次已过结束时间但仍处于报名中的活动，调用同一段逻辑，保证忘记手动结束的活动也能自动收尾。

### 5.2.5 评价实现

提交评价前校验四项：活动状态为已结束、当前用户在该活动有状态为已签到的报名记录、该用户尚未评价过、评分在 1 到 5 之间。评价内容限制 500 字，允许为空（只打分不写文字）。

匿名实现在服务端完成：查询评价列表时，若评价为匿名且查询者既不是作者也不是管理员，则把用户名替换为"匿名同学"并把用户 ID 置空；作者本人仍能看到自己的真实信息，页面上标记"我的评价"。这样前端不需要做任何判断，也不存在前端脱敏被绕过的可能。

### 5.2.6 统计实现

统计模块的 SQL 采用一套动态条件：`<if test="organizerId != null">` 决定是否按组织者过滤。同一个 Mapper 方法，传入组织者 ID 得到"我的活动"数据，传入空值得到全平台数据，避免维护两套几乎相同的 SQL。

趋势数据只查时间列，随后在 Java 层按 `LocalDate` 分组：先按天数生成完整的日期序列，再把每天的报名数与签到数填进去，没有数据的日期补 0。这样前端拿到的数组长度固定，X 轴不会因为某天没有数据而少一格。

签到率的计算口径为 `已签到 / (已签到 + 爽约 + 已报名)`，已取消与被驳回的记录不进入分母，因为它们不代表"应到"。分母为 0 时返回 0，避免除零异常。

## 5.3 前端实现

前端共 19 个页面：登录、注册、404，学生端 7 个（首页、活动中心、活动详情、我的报名、我的评价、消息中心、个人中心），组织者端 5 个（我的活动、发布/编辑活动、报名名单、签到管理、活动数据），管理员端 6 个（活动审核、用户管理、分类管理、公告管理、平台统计、系统参数）。

路由使用 hash 模式，每个路由在 `meta` 中声明标题与允许的角色，全局前置守卫做两件事：未登录时跳转登录页并带上 `redirect` 参数；已登录但角色不符时跳回首页。菜单由角色动态生成，学生只有 6 项，组织者增加 3 项，管理员只有管理相关的 6 项。

页面结构统一为"筛选区 + 内容区 + 分页"三段式，样式集中在 `global.css` 中，主题色选用偏墨绿的颜色而不是 Element 默认的蓝色，一方面更贴近校园气质，另一方面避免看起来像未经修改的模板。

图表页使用 ECharts，折线图展示报名与签到趋势，环形图展示活动分类分布，排行表展示报名人数前 N 的活动。图表容器在窗口尺寸变化时重新 `resize`，防止侧边栏收起后图表变形。

## 5.4 部署实现

系统设计了四种运行形态，覆盖从开发到答辩的不同场景。

**（1）开发形态。** 后端 8080，前端 devServer 8081，通过代理转发 `/api` 与 `/upload`。

**（2）单机 jar。** 前端 `npm run build` 后把 `dist` 内容复制到后端 `static` 目录，`mvn clean package` 生成约 30 MB 的可执行 jar，`java -jar` 启动后访问 `http://localhost:8080` 即可，前后端同源。

**（3）便携包。** 为了让系统能在没有装 Java 和数据库的电脑上直接运行，打包脚本把 jar、JDK 自带的 JRE、建表脚本和启动批处理组装成一个目录，压缩后约 66 MB。启动脚本用相对路径定位内置的 `java.exe`，以 H2 内存库启动，双击即用。这一形态主要用于答辩现场和交给评审老师试用。

**（4）云端。** 后端以 Docker 镜像部署到支持容器的云平台，通过环境变量注入数据库地址与密钥；前端静态资源部署到静态托管平台。由于前后端分属不同域名，需要在后端开启 CORS 并允许携带 `Authorization` 头。

实现过程中遇到一个与部署相关的细节：上传头像时使用 `MultipartFile.transferTo` 传入相对路径，文件会被写到 Tomcat 的临时工作目录，而不是应用的 `upload` 目录，表现为上传成功但访问 404。改为先取 `getAbsoluteFile()` 再写入后问题解决。

# 第6章 系统测试

## 6.1 测试环境与方法

测试在开发机上进行，浏览器使用 Chrome，接口测试借助 PowerShell 脚本直接调用 HTTP 接口，压测使用自行编写的 Java 程序（不依赖第三方库，用 `HttpURLConnection` 发请求、`CountDownLatch` 控制同时起跑）。

测试分为三部分：功能测试覆盖 8 个模块的主要流程与异常分支，共 98 条用例，逐条记录预期与实际结果；并发测试针对报名环节做对照实验；部署测试验证单机、便携、云端三种形态能否正常启动与访问。

测试数据由脚本生成：74 个用户（72 名学生、1 名组织者、1 名管理员）、9 场活动（覆盖草稿、待审核、报名中、已驳回、已结束五种状态）、239 条报名记录（含已报名、已签到、已取消、爽约）、7 条评价。生成脚本会自检每个活动的 `signed_count` 是否等于明细中的有效报名数，不一致则中止，防止演示数据本身出错。

测试过程中发现并修复的缺陷主要有三个：一是上传头像返回 400，原因是 `transferTo` 的相对路径落到了 Tomcat 临时目录；二是待审核状态的活动无法编辑，与需求不符，改为允许草稿、待审核、已驳回三种状态编辑；三是结束活动时爽约人数放在提示语里，前端拿不到数值，改为通过 `data` 返回。

## 6.3 并发对照实验

为了验证名额扣减方案的效果，设计了一组对照实验：同一压测程序、同一活动容量（10 个名额）、同一并发量（50 个学生账号同时报名），分别请求两种实现。

对照组是常见的"先查后改"写法：先查询当前人数，判断是否小于容量，再计算新值写回，并在两次操作之间人为加入 20 毫秒延迟，以放大竞态窗口；实验组是正式实现，即 4.4.1 节的条件更新。

实验结果如表 6-2 所示。

| 指标 | 实验组（条件更新） | 对照组（先查后改） |
| --- | --- | --- |
| 并发请求数 | 50 | 50 |
| 名额上限 | 10 | 10 |
| 报名成功 | 10 | 50 |
| 提示名额已满 | 40 | 0 |
| 耗时 | 77 ms | 212 ms |
| 冗余计数 signed_count | 10 | 6 |
| 明细有效报名数 | 10 | 50 |
| 是否超卖 | 否 | 是，超卖 40 人 |

数据说明两点。第一，条件更新在 50 并发下严格守住了 10 个名额，40 个请求被正确拒绝，计数与明细完全一致。第二，对照组的失败是双重的：不仅 50 人全部报名成功造成超卖，冗余计数也因为丢失更新停在了 6，与实际明细相差 44。这意味着依赖冗余计数展示的"已报名人数"会严重失真，用户在页面上看到的进度条与真实情况不符。

实验组耗时 77 毫秒，平均每个请求不到 2 毫秒，其中包含令牌校验与多次查询；对照组耗时 212 毫秒，多出的时间主要来自人为延迟，但也说明"先查后改"把一次数据库写入拆成了两次读加一次写，事务持有时间更长。

需要说明本实验的边界：并发量只有 50，数据库为单机内存库，未覆盖多实例部署与跨库场景。若把系统扩展到多个后端实例，条件更新仍然有效（因为最终写的是同一个数据库），但若引入分库分表，则需要额外的一致性方案，这一点在 7.2 节讨论。

## 6.4 测试结论

功能层面，系统覆盖了需求文档中的全部功能点，98 条用例全部通过，异常分支的提示信息具体可读，未出现白屏或后端堆栈外泄。并发层面，报名环节在 50 并发下未出现超卖，计数与明细一致，响应时间在可接受范围内。部署层面，单机 jar、便携包、云端三种形态均验证通过：便携包在没有安装 Java 的目录下用内置 JRE 启动成功，首页返回 200；云端实例通过环境变量注入数据库连接后正常读写。

系统仍存在不足：令牌签发后无法立即失效；统计接口在全量数据下未做缓存；缺少操作日志与审计功能。这些问题不影响当前规模下的使用，但在正式推广前需要补齐。

# 第7章 总结与展望

## 7.1 工作总结

本文围绕校园活动的全流程管理，完成了一个基于 Spring Boot 的活动管理系统。主要工作可以概括为四个方面。

第一，梳理了校园活动的业务流程，抽象出学生、组织者、管理员三类角色，明确了活动从草稿到结束的六种状态及其流转条件，形成了覆盖发布、审核、报名、签到、评价、统计的完整闭环。

第二，针对报名环节的超卖问题，采用数据库条件更新实现名额原子扣减，并用唯一索引防重复报名，两者分工明确。对照实验显示，在 50 并发抢 10 个名额的场景下，该方案的报名成功数与明细、计数三者完全一致，而常规的"先查后改"写法超卖 40 人、计数失真 44。

第三，设计了限时签到码、爽约累计与封禁、活动质量分三项机制。签到码降低了现场签到的组织成本，爽约机制对"报名不来"形成了约束，质量分则把签到率、评分与完成率折算成一个直观的数字，供学生参考。

第四，完成了系统的工程化落地，包括 8 个业务模块、40 余个接口、19 个页面、四套初始化脚本与三种部署形态。便携包把 Java 运行时一并打包，使系统可以在未配置开发环境的电脑上直接运行。

## 7.2 不足与展望

系统还存在若干可以改进的地方。

其一是令牌失效问题。当前令牌签发后 7 天内有效，用户被禁用或修改密码后，旧令牌在过期前仍然可用。改进方向是在令牌中加入版本号，用户信息变更时递增版本号，拦截器比对版本号决定是否放行，代价是每次请求多一次用户查询，可以借助本地缓存缓解。

其二是统计性能。当前统计接口每次请求都实时聚合，在数据量增长后可能变慢。可以考虑按天预聚合，把结果写入统计表，接口只读统计表；或者对高频访问的概览数据加短时缓存。

其三是缺少操作日志。管理员审核、用户禁用、参数修改等敏感操作没有留下审计记录，出现问题难以追溯。可以在拦截器或切面中记录操作人、操作类型、目标对象与时间，形成独立的日志表。

其四是移动端体验。当前页面以桌面端为主，手机上虽然可以浏览，但签到页的表格需要横向滚动。后续可以针对签到场景单独做一个移动端页面，只保留签到码输入与结果反馈。

从功能上看，后续还可以增加活动收藏与提醒、候补队列（名额满后排队，有人取消时自动递补）、活动图片的多图上传以及基于历史报名的推荐。这些功能不改变系统的核心结构，可以在现有模块上逐步扩展。
