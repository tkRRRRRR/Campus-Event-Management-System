# 第5章 系统实现

## 5.1 开发环境与项目结构

开发环境为 Windows 11、16 GB 内存；JDK 1.8.0_512、Maven 3.9.9、Node.js 16.20.2；数据库为 MySQL 8.0（云端实例版本为 8.4）；前端依赖包括 Vue 2.7.16、Element UI 2.15.14、axios 1.6.8、ECharts 5.4.3 与 dayjs 1.11.10；后端依赖包括 Spring Boot 2.7.18、MyBatis-Plus 3.5.3.2、mysql-connector-j 8.0.33、H2 1.4.200、java-jwt 3.19.4、hutool 5.8.25 与 Lombok。

后端包名为 `com.campus.activity`，按职责分层：

```
controller   接口层，参数接收与结果包装
service      业务层，校验、事务与状态流转
  impl
mapper       数据访问层，通用方法与自定义 SQL
entity       与表一一对应的实体
dto          入参对象，承载校验注解
vo           出参对象，按页面需要裁剪字段
common       统一返回、业务异常、全局异常处理、常量
config       MyBatis-Plus、Jackson、WebMvc 配置
interceptor  JWT 拦截器
annotation   @RequireRole
task         定时任务
util         JWT 工具、当前用户上下文
```

系统将入参对象与出参对象分离。实体仅用于数据库读写，接口不直接返回实体，以避免密码、报名限制时间等内部字段对外暴露；同时，接收与返回使用不同类型，可避免校验注解相互干扰。

## 5.2 后端实现

### 5.2.1 认证与权限

登录接口接收用户名与密码，先通过 `BCrypt.checkpw` 校验密码，再检查账号状态，通过后签发令牌。为避免通过错误提示判断账号是否存在，账号不存在与密码错误均返回“学号/工号或密码错误”。

拦截器在 `preHandle` 中从请求头获取令牌，校验签名与有效期，解析用户信息并存入 `ThreadLocal`，随后读取处理方法上的 `@RequireRole` 注解完成角色比对；在 `afterCompletion` 中调用 `UserContext.clear()` 清理上下文。由于 Web 容器复用工作线程，若未及时清理，后续请求可能读取到前一次请求的用户身份，因此该清理操作必不可少。

### 5.2.2 活动发布与审核

活动包含草稿、待审核、报名中、已驳回、已取消与已结束六种状态。状态流转集中在业务层实现，所有修改操作均先校验当前状态是否允许该操作。例如，仅草稿、待审核与已驳回的活动可编辑；仅待审核的活动可执行审核；仅报名中的活动可取消，且取消前需校验活动尚未开始。

发布活动时先执行时间校验：开始时间必须晚于当前时间，报名截止时间不得晚于开始时间，结束时间必须晚于开始时间。校验失败时返回具体提示，例如“报名截止时间不能晚于活动开始时间”，而不是笼统的参数错误提示。

审核接口接收通过与驳回两种结果，驳回时强制要求填写理由。理由写入活动记录，并通过消息表向组织者发送通知。组织者可在“我的活动”列表中直接查看驳回理由，无需进入详情页。

取消活动时，系统查询该活动的全部有效报名记录，逐条发送活动取消通知，随后将报名记录置为已取消，并把活动的已占名额置为零。上述操作在同一事务中完成，避免出现通知已发送而状态未更新的情况。

### 5.2.3 报名实现

报名是系统的核心逻辑，代码约 120 行，按顺序完成五项校验后执行名额扣减，关键片段如下：

```java
// 1. 活动必须存在且处于报名中
Activity activity = activityMapper.selectById(activityId);
if (activity == null) throw new BusinessException("活动不存在");
if (activity.getStatus() != Constants.ACTIVITY_PUBLISHED)
    throw new BusinessException("该活动当前未开放报名");
// 2. 报名截止与开始时间
if (now.isAfter(activity.getSignupDeadline()))
    throw new BusinessException("报名已于 " + DATE_FORMAT.format(activity.getSignupDeadline()) + " 截止");
if (!now.isBefore(activity.getStartTime()))
    throw new BusinessException("活动已经开始，无法报名");
// 3. 是否被限制报名
SysUser user = userMapper.selectById(userId);
if (user.getBanUntil() != null && user.getBanUntil().isAfter(now))
    throw new BusinessException("因多次爽约，你被限制报名至 " + ...);
// 4. 是否重复报名（1/2/5 拒绝，4 爽约拒绝，3 已取消则复用原记录）
ActivityRegistration exist = registrationMapper.selectOne(...);
if (exist != null && (status == 1 || status == 2 || status == 5))
    throw new BusinessException("你已报名该活动，请勿重复提交");
if (exist != null && status == 4)
    throw new BusinessException("你上次爽约了该活动，无法再次报名");
// 5. 命中名额
int affected = activityMapper.increaseSignedCount(activityId);
if (affected != 1) throw new BusinessException("名额已满，报名失败");
```

需审核的活动采用另一处理分支：先写入状态为待审核的记录，此时不扣减名额；组织者审核通过时再执行扣减，若名额已满则提示“名额已满，无法通过该报名”，记录保持待审核状态，由组织者决定后续处理。该方式保证名额仅在确定占用时扣减，不会因大量待审核申请而虚占名额。

仅状态为已报名或待审核、且活动尚未开始的报名记录可以取消；若原记录已占用名额，取消时归还名额。

### 5.2.4 签到实现

签到码的生成、查询与校验集中在签到服务中实现。生成时先查询该活动是否存在未过期的签到码，存在则复用；否则生成新码并写入活动表的签到码与过期时间字段，有效期取配置分钟数与活动剩余时间的较小值。

学生签到时，服务端依次校验活动存在、签到码非空、码值匹配、未过期、处于签到时间窗口、报名记录存在且状态为已报名、尚未签到，最后通过条件更新 `set status = 2, checkin_time = now where id = ? and status = 1` 完成状态流转。采用条件更新而非先查询后修改，可避免重复提交导致重复签到。

组织者补签通过独立接口实现，以报名记录标识为参数，允许将爽约记录恢复为已签到，同时将该用户的违约次数减一；若减后低于阈值，则清除报名限制时间，为误判提供补救渠道。

结束活动接口先获取未签到用户列表，批量置为爽约，再逐个累加违约次数并判断是否封禁，最后将活动状态改为已结束。接口返回爽约人数，前端据此给出具体提示。定时任务每 5 分钟扫描一次已过结束时间但仍处于报名中状态的活动，调用相同逻辑处理，保证未手动结束的活动能够自动收尾。

### 5.2.5 评价实现

提交评价前需校验四项条件：活动状态为已结束、当前用户在该活动存在状态为已签到的报名记录、该用户尚未评价、评分在 1 至 5 之间。评价内容限制 500 字，允许为空。

匿名处理在服务端完成：查询评价列表时，若评价为匿名且查询者既非作者也非管理员，则将用户名替换为“匿名同学”并置空用户标识；作者本人仍可查看真实信息，页面标记为“我的评价”。该方式使前端无需进行额外判断，也避免了前端脱敏被绕过的可能。

### 5.2.6 统计实现

统计模块的 SQL 采用动态条件，通过 `<if test="organizerId != null">` 判断是否按组织者过滤。同一 Mapper 方法在传入组织者标识时返回组织者维度的数据，传入空值时返回平台维度的数据，避免维护两套近似语句。

趋势数据仅查询时间字段，随后在 Java 层按 `LocalDate` 分组：先生成完整日期序列，再填充每日的报名数与签到数，无数据的日期补 0。该处理保证返回数组长度固定，避免前端横轴缺少刻度。

签到率的计算口径为已签到人数与（已签到 + 爽约 + 已报名）人数之比，已取消与被驳回的记录不计入分母，因其不属于应到范围。分母为 0 时返回 0，避免除零异常。

## 5.3 前端实现

前端共 21 个页面：登录、注册、404 页面，学生端 7 个（首页、活动中心、活动详情、我的报名、我的评价、消息中心、个人中心），组织者端 5 个（我的活动、发布与编辑活动、报名名单、签到管理、活动数据），管理员端 6 个（活动审核、用户管理、分类管理、公告管理、平台统计、系统参数）。

路由采用 hash 模式，每个路由在 `meta` 中声明标题与允许访问的角色，全局前置守卫完成两项判断：未登录时跳转至登录页并携带重定向参数；已登录但角色不符时返回首页。导航菜单按角色动态生成，学生为 6 项，组织者增加 3 项，管理员为管理相关 6 项。

页面结构统一为筛选区、内容区与分页区三段式，通用样式集中于 `global.css`。主题色采用墨绿色，以契合校园场景，并与组件库默认配色区分。

图表页面使用 ECharts 实现，折线图展示报名与签到趋势，环形图展示活动分类分布，排行榜展示报名人数前若干位的活动。图表容器在窗口尺寸变化时重新调整尺寸，避免侧边栏收起后图表变形。

## 5.4 部署实现

系统设计了四种运行形态，覆盖开发与演示等场景。

**（1）开发形态。** 后端运行于 8080 端口，前端开发服务器运行于 8081 端口，通过代理转发 `/api` 与 `/upload` 请求。

**（2）单机可执行程序。** 前端执行 `npm run build` 后，将构建产物复制至后端 `static` 目录，经 `mvn clean package` 生成约 30 MB 的可执行 JAR，通过 `java -jar` 启动后访问 `http://localhost:8080`，前后端同源。

**（3）便携运行包。** 为使系统可在未安装 Java 与数据库的计算机上运行，打包脚本将可执行 JAR、JDK 自带的 Java 运行环境、建表脚本与启动脚本组装为独立目录，压缩后约 66 MB。启动脚本通过相对路径定位内置的 Java 可执行文件，以 H2 内存数据库启动。该形态主要用于答辩现场演示与评审试用。

**（4）云端部署。** 后端以 Docker 镜像形式部署至支持容器的云平台，通过环境变量注入数据库连接信息与密钥；前端静态资源部署至静态托管平台。由于前后端处于不同域名，后端需开启跨域配置并允许携带认证头。该形态已实际部署：前端托管于 Vercel（campus-activity-web.vercel.app），后端以 Docker 镜像运行于 Render（campus-activity-api.onrender.com），数据库使用云端 MySQL。免费实例在空闲 15 分钟后休眠，首次访问需 30 至 60 秒唤醒，故现场演示仍以便携包为主。

部署过程中需注意文件上传路径的处理：使用 `MultipartFile.transferTo` 传入相对路径时，文件将被写入 Web 容器的工作目录而非应用的 `upload` 目录，表现为上传成功但访问失败。实现中改为先获取绝对路径再写入，问题得以解决。

# 第6章 系统测试

## 6.1 测试环境与方法

测试在开发机上进行，浏览器使用 Chrome，接口测试通过 PowerShell 脚本直接调用 HTTP 接口，并发测试使用自行编写的 Java 程序，该程序不依赖第三方库，通过 `HttpURLConnection` 发送请求，通过 `CountDownLatch` 控制并发起跑。

测试分为三部分：功能测试覆盖 8 个模块的主要流程与异常分支，共 104 条用例，逐条记录预期结果与实际结果；并发测试针对报名环节设计对照实验；部署测试验证单机可执行程序与便携包能否在未配置开发环境的计算机上启动，以及连接云端 MySQL 时的读写是否正常。

测试数据由脚本生成，包括 74 个用户（72 名学生、1 名组织者、1 名管理员）与 8 场种子活动；测试过程中另创建 1 场活动用于演示签到，故界面中活动总数为 9；报名记录 239 条，评价 7 条。生成脚本会校验每个活动的报名计数是否等于有效报名明细数，不一致时终止执行。早期版本采用手工编写的数据，曾出现计数与明细不一致的情况，导致报名进度与名单显示不符，后改为脚本生成并自检。

除表中用例外，测试还覆盖了头像上传与静态资源访问、密码修改后需重新登录、活动取消后报名者收到通知、组织者仅能查看本人活动的报名名单等场景。104 条用例全部通过，未发现阻塞性问题。

测试过程中发现并修复的缺陷主要有三处：一是头像上传返回 400，原因为相对路径导致文件写入 Web 容器临时目录；二是待审核状态的活动无法编辑，与需求不符，已调整为允许草稿、待审核与已驳回三种状态编辑；三是结束活动时爽约人数仅通过提示语返回，前端无法获取数值，已改为通过响应数据返回。

## 6.3 并发对照实验

为验证名额扣减方案的效果，设计了一组对照实验：使用同一并发测试程序、同一活动容量（10 个名额）与同一并发量（50 个学生账号同时报名），分别请求两种实现。

对照组为常见的“先查询后更新”写法：先查询当前报名人数，判断是否小于容量，再计算新值写回，并在两次操作之间加入 20 毫秒延迟以放大竞态窗口；实验组为正式实现，即 4.4.1 节所述的条件更新。

实验结果如表 6-2 所示。

| 指标 | 实验组（条件更新） | 对照组（先查后改） |
| --- | --- | --- |
| 并发请求数 | 50 | 50 |
| 名额上限 | 10 | 10 |
| 报名成功 | 10 | 50 |
| 提示名额已满 | 40 | 0 |
| 耗时 | 77 ms | 212 ms |
| 冗余计数 signed_count | 10 | 6 |
| 明细有效报名数 | 10 | 50 |
| 是否超卖 | 否 | 是，超卖 40 人 |

实验结果表明两点。第一，条件更新在 50 并发下严格保持了 10 个名额的上限，40 个请求被正确拒绝，计数与明细完全一致。第二，对照组的失效具有双重性：不仅 50 个请求全部报名成功造成超卖，冗余计数也因丢失更新停留在 6，与明细相差 44，导致界面展示的报名进度与实际情况不符。

实验组耗时 77 毫秒，平均每个请求不足 2 毫秒，其中包含令牌校验与多次查询；对照组耗时 212 毫秒，额外时间主要来自人为延迟，同时也说明“先查询后更新”将一次写入拆分为两次读取与一次写入，事务持有时间更长。

本实验存在一定边界：并发量为 50，数据库为单机内存库，未覆盖多实例部署与跨库场景。若系统扩展为多个后端实例，条件更新仍然有效，因为写入目标为同一数据库；若引入分库分表，则需额外的一致性方案，相关讨论见 7.2 节。

## 6.4 测试结论

功能层面，系统覆盖了需求中的全部功能点，104 条用例全部通过，异常分支的提示信息明确，未出现页面异常或异常堆栈泄露。并发层面，报名环节在 50 并发下未出现超卖，计数与明细一致，响应时间满足要求。部署层面，单机可执行程序与便携包均在本机完成实测：便携包在未安装 Java 的目录下通过内置运行环境启动成功，首页返回 200；连接云端 MySQL 8.4 的版本也完成了增删改查验证。云端形态同样完成实测：前端部署于 Vercel，后端以 Docker 镜像运行于 Render，接口经跨域访问正常，首页、登录、活动列表与名单导出均返回 200；受免费实例休眠与容器临时文件系统限制，上传的封面在重启后会丢失，线上仅作为部署能力的验证，不承担长期运行。

系统仍存在不足：令牌签发后无法立即失效；统计接口未做缓存；缺少操作日志与审计功能。上述问题在当前使用规模下影响有限，但在正式推广前需要补齐。

# 第7章 总结与展望

## 7.1 工作总结

本文围绕校园活动的全流程管理，完成了一个基于 Spring Boot 的活动管理系统。主要工作可概括为四个方面。

第一，完成了业务流程与角色职责的梳理。明确了学生、组织者与管理员三类角色的功能边界，以及活动从草稿到结束的状态流转与触发条件。该梳理最终落实为 8 张数据表与 60 个接口，并作为测试用例设计的依据。

第二，针对报名环节的超卖问题，采用数据库条件更新实现名额原子扣减，并结合唯一索引防止重复报名，两者职责明确。对照实验显示，在 50 并发竞争 10 个名额的条件下，报名成功数、明细记录与计数三者一致；而“先查询后更新”的实现导致超卖 40 人，计数比明细少 44。

第三，设计了限时签到码、爽约累计与报名限制、活动质量分三项机制。签到码使现场签到不再依赖纸质名单；爽约机制对报名后缺席形成约束；质量分将签到率、评分与完成率折算为单一指标，供学生与组织者参考。

第四，完成了系统实现与工程交付：8 个业务模块、60 个接口、21 个页面、三份初始化脚本，以及开发、单机可执行程序、便携运行包与云端配置四种运行形态，其中前三种已完成实际运行验证。便携包内置 Java 运行环境，可在未配置开发环境的计算机上直接启动。

## 7.2 不足与展望

系统仍存在若干可改进之处。

第一，令牌失效问题。当前令牌签发后 7 天内有效，用户被禁用或修改密码后，旧令牌在过期前仍可使用。改进方向是在令牌中加入版本号，用户信息变更时递增版本号，由拦截器比对版本号决定是否放行；该方案会增加一次用户查询，可通过本地缓存缓解开销。

第二，统计性能。当前统计接口每次请求均实时聚合，数据量增长后响应时间可能上升。可考虑按天预聚合，将结果写入统计表，接口仅读取统计结果；或对访问频繁的概览数据增加短时缓存。

第三，缺少操作日志。管理员审核、账号禁用与参数修改等敏感操作未留下审计记录，出现问题难以追溯。可在拦截器或切面中记录操作人、操作类型、目标对象与操作时间，形成独立的日志表。

第四，移动端体验。当前页面以桌面端为主，移动端虽可浏览，但部分列表需要横向滚动。后续可针对签到场景设计独立的移动端页面，仅保留签到码输入与结果反馈。

在功能层面，后续可增加活动收藏与提醒、候补队列（名额满后排队，有人取消时自动递补）、活动多图上传以及基于历史报名的推荐。上述功能不改变系统的核心结构，可在现有模块基础上逐步扩展。
